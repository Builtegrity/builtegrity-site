# Builtegrity Transaction Engine — V1 Runbook

## Current architecture

V1 uses a Cloudflare Worker with Static Assets, D1, and R2. Stripe is the payment processor. Clerk is the application identity/session provider. Resend is both the transactional-email adapter and, for the dedicated legal receiving route, a verified inbound-email adapter. Turnstile is a public-route abuse-protection adapter where appropriate.

Builtegrity stores transaction context, merchant-scoped customer relationships, consent, normalized processor references, first-class events, exceptions, economics, payout reconciliation, statement/tax/accounting evidence, and legal/compliance state.

Core hierarchy:

`Partner -> Merchant -> merchant-scoped Customer -> Purchase -> Transaction -> Transaction Data / Events / Exceptions`

Direct merchants are grouped under `PARTNER-0001` / Builtegrity Direct.

Identity and authorization are separate: Clerk proves identity; Builtegrity/D1 decides tenant/role/data access.

## Canonical sources

- Database schema: ordered `migrations/*.sql` only.
- Cross-system contract: `ops/system-contract.json`.
- Transaction vocabulary: `transaction-engine/definitions.json` plus the system contract.
- Runtime: `worker/src/`.
- Canonical application/public assets: `public/`.
- Owner/provider readiness: `ops/owner-control-manifest.json`.

A standalone database schema snapshot is intentionally forbidden.

## Three transaction-state axes

### Lifecycle

`CREATED -> CONSENTED -> PAYMENT_PENDING -> PAID -> PAYOUT_PENDING -> COMPLETE`

Lifecycle answers where the transaction is operationally. Historical lifecycle truth is not rewritten merely because a later refund/dispute occurs.

### Integrity

`INCOMPLETE | ACCOUNTED | NEEDS_ATTENTION`

`ACCOUNTED` is an integrity/completeness state. It means the required transaction/processor/payout evidence has been captured and no unresolved integrity exception remains under the active rules.

### Record / revenue classification

`PENDING_PROTECTED | PROTECTED | OBSERVED | IMPORTED | FEE_EXCEPTION`

Merchant-facing classes are `PROTECTED`, `OBSERVED`, and `IMPORTED`.

`PROTECTED` is a record/revenue classification. It requires the controlled Builtegrity payment route, successful payment history, and processor-confirmed Builtegrity application-fee evidence satisfying the locked fee invariant.

`ACCOUNTED` and `PROTECTED` are different axes and must never be substituted for one another.

Only `PROTECTED` transactions can create Builtegrity transaction-fee revenue. OBSERVED and IMPORTED transactions can be documented/reconciled but do not create the protected transaction fee.

## Pricing and fractional carry

The implemented pre-launch pricing candidate is `BG_STANDARD_V1`, defined in runtime/migrations and represented in `ops/system-contract.json`.

Transaction fee entitlement is calculated in micros. Stripe application-fee collection occurs in whole smallest-currency units. A sub-cent residual is accrued to a merchant/currency carry ledger. Later whole-cent carry settlement collects prior entitlement; it is not new fee entitlement earned by the later payment.

Keep these separate everywhere:

- exact transaction-fee entitlement;
- gross application-fee cash on a payment;
- current retained application-fee cash after fee refunds;
- residual generated by the current transaction;
- prior carry settled on the current payment.

Pricing implementation does not mean commercial approval. LIVE requires explicit owner lock and all separate legal/compliance approvals.

## Platform Fee refunds/disputes

The implemented candidate policy is `FEE-REFUND-POLICY-V1`. Runtime supports several reviewed handler shapes including retain-if-earned, full-fee refund, and pro-rata refund patterns.

The applicable rule is locked to the transaction before Checkout. Missing/expired/blocked/unimplemented treatment fails closed. Builtegrity error/duplicate/overcharge and applicable law/processor requirements can create automatic fee refunds/credits.

The candidate economic default is not live authority until owner-locked and counsel/jurisdiction approved.

## Stripe Connect onboarding

The first-merchant lane is an eligible existing Stripe merchant capable of the intended Connect relationship.

`POST /api/merchants/:merchant_id/stripe/connect-url`

creates a one-time OAuth state and Stripe authorization URL. The callback stores the connected `acct_...` account reference. Verification confirms required charges/payout capability and V1 automatic-payout compatibility.

Manual payout merchants do not receive the full transaction-to-automatic-payout V1 promise.

## Transaction creation and customer flow

Internal transaction creation:

`POST /api/transactions`

A transaction receives a permanent TX ID, random public payment token, terms/consent evidence, pricing/refund-policy snapshot, and initial event.

Customer flow:

1. customer opens the tokenized payment page;
2. Builtegrity displays merchant/purchase/amount/terms;
3. customer explicitly accepts;
4. exact acceptance evidence/hash is stored;
5. server creates Stripe Checkout on the connected merchant account;
6. payment-card credentials are entered only on Stripe-hosted surfaces;
7. browser return never proves payment success; signed server-side processor events do.

## Stripe event handling

Webhook endpoint:

`POST /api/webhooks/stripe`

Raw body + Stripe signature verification are mandatory. Webhook receipts are idempotent and transaction events are append-oriented.

Payment/application-fee event order is not trusted. Protection is confirmed only when durable payment and fee facts satisfy the invariant, regardless of arrival order. If payment success is known but fee evidence is missing/mismatched, the transaction remains internal `FEE_EXCEPTION`/attention state until corrected evidence arrives or the case resolves.

## Email surfaces

### Transactional outbound email

Resend sends confirmations, statements, and selected alerts. Email delivery can never rewrite payment truth.

### Legal inbound email

A dedicated Resend receiving subdomain/address can accept legal notices at the verified legal-inbox webhook. Inbound content is untrusted evidence, never executable instructions. It is signature-verified, hashed/preserved, placed under legal response controls, and routed to actual standing counsel when configured.

ChatGPT/Atlas is not counsel.

## Statements

Monthly statement format V2 uses `record_classification='PROTECTED'`—not successful payment status—to calculate protected count/volume.

Statements separately expose exact fee entitlement, gross application-fee cash, current retained fee cash, and prior carry settlement. Partner statements remain merchant-summary-level by default to preserve customer-data boundaries.

## Books and tax reconciliation

Company books consume the ACTUAL transaction economics ledger and adjustment evidence; they do not infer revenue from marketing/reporting labels.

Year-end payment summaries separate PROTECTED/OBSERVED/IMPORTED and remain informational reconciliation aids. Stripe/tax authorities remain authoritative for official processor tax forms/rules. Builtegrity does not turn payment-summary output into automatic tax advice/filing.

## Financial safety

The machine evaluates current unit economics, processor responsibility/balance evidence, company financial position, cost-model freshness, support/human-touch pressure, and reserves.

A green legal/processor state cannot override a red/unknown financial-safety state, and vice versa.

Current canonical thresholds are mirrored in `ops/system-contract.json` and documented in `docs/financial-safety.md`.

## Legal/compliance response

Legal automation handles process/routing, not legal judgment. High-risk notices/security events are preserved and routed to qualified authority. Holds cannot be released and legal incidents cannot be closed through untrusted input.

“Counsel” means an actual retained outside attorney/law firm under active engagement. Until that provider and response route are verified, the legal-response program remains a LIVE blocker.

## Hard V1 boundaries

Do not enable without a new versioned design/legal/compliance review:

- incompatible merchants already controlled by another Connect platform;
- manual payouts while promising transaction-to-payout reconciliation;
- subscriptions;
- marketplaces/funds routing;
- international merchants/customer transactions;
- non-USD protected payments;
- raw card handling;
- escrow/stored value/money transmission;
- claims of insurance, fraud/chargeback protection, guaranteed legal enforceability, guaranteed payout, or independent bank-deposit verification.
