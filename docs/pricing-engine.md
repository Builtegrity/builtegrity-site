# Builtegrity Pricing Engine

## Canonical V1 candidate

The implemented pre-launch pricing candidate is `BG_STANDARD_V1`.

It is intentionally represented in `ops/system-contract.json` as an **implemented test candidate**, not as an owner-locked commercial decision. Code, tests, and draft disclosure can exist before the owner has explicitly locked the commercial schedule. `npm run system:gate:live` must fail until that owner lock exists and all separate legal/compliance gates pass.

The candidate schedule is:

| Payment amount | Base fee | Percentage |
| --- | ---: | ---: |
| $0.01–$1.00 | 1¢ | + 0.10% |
| $1.01–$5.00 | 2¢ | + 0.10% |
| $5.01–$10.00 | 3¢ | + 0.10% |
| $10.01+ | 5¢ | + 0.10% |

There is no setup fee, no monthly subscription, and no upper fee cap in `BG_STANDARD_V1`.

## One price, several different economic facts

Do not collapse these into one number:

1. **Transaction fee entitlement** — the exact fee attributable to this transaction, stored in micros and entitled only after that transaction becomes PROTECTED.
2. **Whole-cent processor fee** — the current transaction's whole-cent amount attached to Stripe.
3. **Current residual** — the sub-cent remainder generated by this transaction; it does not enter available carry until PROTECTED.
4. **Prior carry reserved/settled** — whole cents of previously entitled residual reserved before a later checkout and settled only if that later payment becomes PROTECTED.
5. **Gross application-fee cash** — current whole-cent fee plus any settled prior carry actually processor-confirmed on this payment.
6. **Current retained fee cash** — gross application-fee cash less any later application-fee refund/credit.

A later payment that settles 1¢ of prior fractional carry did not earn an extra 1¢ of fee entitlement for that later transaction. It collected prior entitlement. Reporting, books, statements, tax workpapers, and economics must preserve that distinction.

## Exact fee calculation

For an amount-band transaction:

`exact fee micros = base fee micros + amount_cents × percentage_bps`

For `BG_STANDARD_V1`, `percentage_bps = 10`, which is 0.10%.

Examples before carry settlement:

| Payment | Exact transaction fee |
| ---: | ---: |
| $0.99 | 1.099¢ |
| $5.00 | 2.500¢ |
| $10.00 | 4.000¢ |
| $20.00 | 7.000¢ |
| $100.00 | 15.000¢ |
| $500.00 | 55.000¢ |
| $1,000.00 | $1.05 |

The pricing engine floors the current processor collection to whole cents rather than rounding every fractional result upward.

## Fractional-cent carry

Stripe application-fee collection operates in the currency's smallest unit. Builtegrity therefore keeps exact internal fee attribution in micros while collecting only whole cents through the processor.

The carry lifecycle is:

`AVAILABLE → RESERVED before Checkout → SETTLED only at PROTECTED`

If a transaction later becomes PROTECTED and creates a residual below one cent, that residual becomes entitled and enters the merchant/currency carry ledger. When available carry reaches at least one whole cent, a later checkout can reserve whole-cent carry atomically. If checkout is abandoned before payment, the reservation can be released. If payment succeeds but the required Builtegrity application fee is missing/mismatched, the transaction remains non-PROTECTED and the reserved carry remains releasable. Only processor-confirmed PROTECTED completion settles the reservation.

This matters because **payment success alone is not a Builtegrity fee-earning event**.

The carry ledger is merchant- and currency-scoped, append-audited, and protected against concurrent double reservation.

## PROTECTED is the revenue gate

Pricing a transaction is not revenue recognition.

A transaction can create Builtegrity transaction-fee entitlement only when it becomes `PROTECTED`. PROTECTED requires all of the following:

- Builtegrity-controlled protected route;
- required customer jurisdiction attestation;
- pre-checkout legal-gate evidence;
- successful processor payment history; and
- processor-confirmed gross application-fee evidence matching the current transaction's locked whole-cent fee plus any valid reserved prior carry.

Real Stripe payment/fee facts are still recorded if a legal prerequisite is missing. The record simply cannot be promoted to PROTECTED and is routed to review. Processor truth is never discarded to make a compliance gate look clean.

`OBSERVED` and `IMPORTED` records never create Builtegrity transaction-fee revenue. Internal `PENDING_PROTECTED` and `FEE_EXCEPTION` states are not merchant-facing revenue classes.

`ACCOUNTED` is a separate integrity/completeness state and must never be used as a substitute for `PROTECTED` when calculating revenue.

## Entitlement versus cash accounting

`transaction_fee_entitlements` preserves the exact fee attributable to the originating PROTECTED transaction in micros.

The ACTUAL transaction-economics revenue entry is a separate **cash-receipt fact** based on the processor-confirmed whole-cent application fee. That cash receipt can include prior carry settlement. Cash-basis company books may reconcile that actual receipt without treating the prior carry as newly earned entitlement for the later transaction.

This separation prevents both revenue loss and double attribution.

## Refunds, disputes, and Platform Fee economics

Pricing and Platform Fee refundability are deliberately separate policies.

The current implemented fee/refund candidate is `FEE-REFUND-POLICY-V1`. Its candidate default is `RETAIN_IF_EARNED`, but that is not permission for live use. The system supports stricter full and proportional refund handlers, resolves applicable merchant/customer jurisdiction rules, and fails closed when the rule is missing, expired, blocked, or lacks a tested handler.

The fee/refund candidate remains subject to two independent approvals before LIVE:

- explicit owner lock of the economic policy; and
- applicable counsel/jurisdiction/processor approval.

A verified Builtegrity overcharge, duplicate collection, fee collected without the fee-earning conditions, or another approved legal/processor rule can create an automatic fee refund or credit.

## Historical immutability

Every transaction locks its pricing version and fee/refund compliance evidence before Checkout. Later pricing changes create a new version; they do not recalculate historical transactions.

Historical protection and gross application-fee evidence remain append-oriented/immutable. Later refunds, credits, disputes, corrections, and carry reconciliations are adjustments/correction evidence rather than rewrites of the original event.

Historical D1 migrations are also immutable after the system baseline. Correct old behavior with a new migration; never edit applied migration history.

## Financial-safety coupling

The active pricing candidate is coupled to explicit economic guardrails:

- minimum floor planning margin: **80%**;
- target human-touch rate: **0.01%**;
- mature human-touch target: **0.005%**;
- warning/orange human-touch threshold: **0.02%**;
- critical/red human-touch threshold: **0.05%**;
- Platform Fee reversal/credit planning reserve: **0.5%**;
- low-ticket effective-rate watch threshold: **1.50%**.

These values live in the runtime database policy and are mirrored in `ops/system-contract.json`. Documentation may explain them but must not become a competing source of truth.
